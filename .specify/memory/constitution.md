# MesureMG Constitution

## Core Principles

### I. Deploy-Ready

The application MUST be deployable to Vercel at any point in the development cycle. This means:
- All environment variables MUST be documented and configurable via Vercel settings
- Build process MUST complete reliably in under 3 minutes
- No local-only dependencies or build artifacts required for deployment
- Each commit to main branch is production-ready or clearly marked as WIP

**Rationale**: Enables rapid feedback loops and unblocks demo/sharing at any time. Prevents "works locally" surprises.

### II. Self-Contained

The application MUST include all necessary configuration, dependencies, and documentation to run standalone without external setup:
- Package.json fully specifies all runtime and dev dependencies
- .env.example documents all required environment variables
- README includes setup, build, and run instructions
- No implicit assumptions about local environment (Node versions, OS-specific tools)

**Rationale**: Reduces friction for sharing the project and enables reproducible deployments across machines.

### III. Shareable & Accessible

The deployed app MUST be instantly usable via a public Vercel link without authentication barriers (unless specified in feature requirements):
- No forced login for default use cases
- Fast initial page load (Core Web Vitals: LCP <2.5s, CLS <0.1)
- Mobile-responsive and touch-friendly by default
- Clear error messages, no cryptic failures

**Rationale**: The primary value is ease of sharing and low-friction user adoption. A broken link or slow load kills that value.

### IV. Performance-First

Every component MUST prioritize performance:
- API responses cached aggressively (static or revalidation strategy declared)
- Client-side state management minimal (prefer server-driven UI)
- Image/asset optimization: next/image or equivalent, no unoptimized files shipped
- Bundle size monitored; new dependencies justified in pull requests

**Rationale**: Vercel bandwidth and response time directly impact user experience and sharing appeal. Small, fast wins.

### V. Production Quality

Code shipped to main branch MUST meet production standards even in early stages:
- Feature branches tested locally before merge (manual or automated)
- No console warnings/errors in production build
- Error handling explicit (no silent failures)
- Code follows project style guide (enforced via linting)

**Rationale**: Prevents technical debt from accumulating and keeps the app shareable with confidence.

## Technology Stack

**Frontend Framework**: Next.js (or similar React-based framework optimized for Vercel)

**Styling**: Tailwind CSS or CSS Modules (consistent, maintainable)

**Runtime**: Node.js LTS (version pinned in package.json and .nvmrc)

**API/Backend**: Serverless functions (Vercel Functions) or headless CMS if needed

**Database**: Optional; if used, MUST be serverless-compatible (e.g., Supabase, Planetscale, or similar)

**Testing**: Minimal but required—Jest + React Testing Library for critical paths

**Deployment**: Vercel (built-in CI/CD, automatic preview deployments on PRs)

**Version Control**: Git with main branch as production-ready

## Deployment & Sharing

**Environment Configuration**:
- All secrets and variables defined in `.env.local` (local) and Vercel project settings (production/preview)
- `.env.example` MUST be committed; `.env.local` MUST be gitignored
- Build process MUST NOT fail if optional variables are missing (graceful degradation)

**Vercel Deployment**:
- Production: Automatic deployment on merge to main
- Preview: Automatic preview deployment on every PR
- Rollback: Latest working commit available via Vercel dashboard; rollback allowed without special approval
- Domain: Custom domain configured via Vercel DNS; shareable link always stable

**Public Sharing**:
- Vercel deployment link is the canonical share URL
- No manual deployment steps required to update shared link
- Link lifespan: indefinite (unless explicitly deprecated in documentation)

## Development Workflow

**Local Development**:
1. Clone repo → `npm install` → `npm run dev`
2. Develop features on feature branches
3. Test locally (manual or automated)
4. Commit and push → PR auto-deployed to preview
5. Merge to main on approval → auto-deployed to production

**Code Review**:
- PR MUST include a preview link (auto-generated by Vercel)
- Reviewer tests on preview; visual changes expected
- No merge to main until preview is approved

**Versioning** (Semantic):
- MAJOR: Breaking API changes, deployment strategy changes
- MINOR: New features, principle additions
- PATCH: Bug fixes, docs, performance improvements
- Tag releases in git (optional for early stage; encourage when sharing with users)

## Governance

**Constitution Authority**: This constitution supersedes all other project practices and guides decisions on architecture, deployment, and feature scope.

**Amendment Procedure**:
- Proposed amendments MUST be documented in a pull request with rationale
- Changes to Core Principles require explicit approval (async-OK; document in commit message)
- Changes to deployment strategy MUST be tested on a staging/preview deployment first
- Amendments are recorded with date in constitution header

**Compliance Review**:
- Every merge to main MUST pass automated checks (build, lint, tests)
- Production deployments MUST validate Core Principles (esp. Deploy-Ready, Shareable)
- Manual spot-checks monthly on shared link performance and accessibility

**Development Guidance**: Refer to `.specify/memory/CLAUDE.md` for runtime decision-making and Claude Code conventions. Refer to `CONTRIBUTING.md` (if exists) for contribution standards.
